# 검증 절차와 함정

이 문서가 관리지침서에서 가장 중요합니다. 코드는 검색하면 나오지만 "고쳐졌는지 확인하는 순서"는 한 번 겪어봐야 몸에 남습니다.

**전제: "작업 완료" 보고는 증거가 아닙니다.** AI 도구의 것이든, 사람의 것이든, 자기 자신의 것이든 마찬가지입니다. 코드가 맞게 생긴 것과 렌더된 태그가 맞는 것은 다른 사실이고, 둘 사이에는 빌드·배포·캐시 세 단계가 있습니다.

---

## 검증 순서

### 1단계 — 푸시 전 로컬 빌드

```bash
npm run build
```

로그 원문을 읽으세요. 요약하지 말고. 볼 것:

- **타입 에러** — 메타데이터 객체 형태를 바꿨을 때 여기서 잡힙니다
- **라우트별 렌더링 방식 표시** — `generateMetadata`를 추가하면서 정적(`○`)이던 라우트가 동적(`ƒ`)으로 바뀌면 여기서 드러납니다. 사이트맵 자동 수집과 성능에 직접 영향을 주므로 그냥 넘기면 안 됩니다
- **First Load JS** — 죽은 코드를 지웠다면 전후를 기록해 두세요. 다음 계약 자료가 됩니다
- **postbuild(next-sitemap) 출력** — 생성된 URL 개수

서버에 올려서 확인하면 한 번에 5분씩 날아갑니다.

### 2단계 — 로컬에서 렌더된 `<head>` 확인

```bash
npm run start
# 다른 터미널에서
curl -s http://localhost:3000/ko/capabilities | grep -iE '<title>|name="description"|rel="canonical"|hreflang'
```

또는 브라우저에서 `Ctrl+U` → `Ctrl+F`로 `canonical`, `hreflang`, `ld+json` 검색. 30초면 됩니다.

**반드시 여러 페이지를 비교하세요.** canonical과 title은 페이지마다 달라야 정상입니다. 세 페이지가 같은 값이면 아직 안 고쳐진 겁니다.

그리고 **서로 다른 언어의 같은 라우트**도 비교하세요. 이걸 안 하면 언어별 미분기를 영원히 못 찾습니다. 실제로 그래서 몇 달을 놓쳤습니다.

### 3단계 — 수정 전후 대조표

이게 사용자에게 보여줄 산출물입니다.

```
라우트          언어   수정 전 title                       수정 후 title
/              ko     THE PRIME DAON | 완벽한 가죽...     가죽 케이스 OEM 제조
/capabilities  ko     THE PRIME DAON | 완벽한 가죽...     레이저 가공·정밀 미싱 생산설비
/capabilities  en     THE PRIME DAON | 완벽한 가죽...     Leather Manufacturing Capabilities
/capabilities  ja     THE PRIME DAON | 완벽한 가죽...     レザー製造設備・加工工程
```

전후를 나란히 놓으면 **안 바뀐 칸**이 즉시 보입니다. "전부 반영했습니다"라는 문장으로는 절대 안 보이고, 실제로 한두 칸이 빠지는 일이 흔합니다.

### 4단계 — 배포 후, 도메인 말고 배포 주소부터

Vercel이면 `.vercel.app` 주소로 먼저 확인하세요. 도메인은 CDN 캐시가 껴서 옛날 내용을 보여줄 수 있습니다.

배포 대시보드에서 **상태를 눈으로 확인**하세요. 빌드가 실패하면 이전 배포가 그대로 유지되기 때문에, 사이트는 멀쩡히 떠 있는데 내용만 옛날 버전인 상태가 됩니다.

### 5단계 — 도메인에서 최종 확인

1단계와 똑같은 항목을 라이브에서 다시 수집합니다. 대표 페이지 3개면 충분합니다: 같은 언어 다른 라우트 2개 + 다른 언어 같은 라우트 1개.

### 6단계 — 도구 검증

- **구글 리치 결과 테스트** — `search.google.com/test/rich-results`에 주소를 넣으면 JSON-LD를 검증해줍니다
- **PageSpeed Insights** — 이미지 작업 전후 모바일 점수를 기록
- **개발자도구 Network** — 쇼룸 초기 이미지 요청 수와 전송량

### 7단계 — 한 달 뒤 재측정

서치콘솔에서 노출수·클릭수 변화를 기록하세요. **이 전후 비교가 다음 계약을 따는 자료가 됩니다.** 색인 반영에는 수일에서 수주가 걸리므로 수정 직후 결과를 기대하지 마세요.

## 서치콘솔 판독

### "성공"만으로 판정하지 않는다

서치콘솔의 "성공"은 **XML을 문법 오류 없이 읽었다**는 뜻이지 내용이 맞다는 뜻이 아닙니다. 실제 판정은 두 숫자를 맞춰보는 것입니다.

| 대조할 값 | 어디서 |
|---|---|
| 실제 sitemap.xml의 `<loc>` 개수 | 브라우저에서 sitemap.xml 열고 `Ctrl+F`로 `<loc>` 검색 |
| 서치콘솔 "발견된 페이지" | Sitemaps 화면 |

두 값이 같으면 정상. 다르면 성공 표시가 떠 있어도 문제입니다.

**현재 기준값: 23.** P1-4 작업 후에는 26이 되어야 합니다(`/en` 홈 1개 + `/contact` 4개 언어).

### 속성 유형은 화면 구조에서 역산한다

서로 다른 호스트(www와 non-www)의 사이트맵이 **한 테이블에 나란히, 둘 다 성공**으로 있으면 그 속성은 **도메인 속성**입니다. URL 접두어 속성이었다면 다른 호스트의 사이트맵은 등록 단계에서 거부되기 때문입니다.

반대로 www 사이트맵 제출이 계속 실패한다면 속성이 non-www URL 접두어로 잡혀 있을 가능성이 높고, **그때는 재제출을 아무리 반복해도 해결되지 않습니다.** 도메인 속성으로 다시 잡아야 합니다.

프라임다온은 도메인 속성으로 확인됐습니다.

### 오래된 사이트맵 항목 삭제

**삭제해도 이미 색인된 페이지는 색인에서 빠지지 않습니다.** 제출 기록만 지워집니다. 이 확신이 없으면 못 지우고 헷갈리는 화면을 계속 안고 가게 됩니다.

⚠️ Sitemaps 화면의 **'사이트맵 삭제'**와 좌측 메뉴의 **'삭제' 도구(Removals)**는 완전히 다릅니다. Removals는 URL을 검색결과에서 약 6개월간 숨기는 기능이라 여기에 도메인을 넣으면 사이트가 검색에서 통째로 사라집니다. **Sitemaps 화면 안에서만** 작업하세요.

지우기 전에 apex와 www **양쪽 robots.txt**의 `Sitemap:` 줄이 정식 호스트를 가리키는지 확인하세요. 아니면 얼마 뒤 "감지된 사이트맵"으로 다시 나타납니다.

## 함정 목록

프라임다온 작업에서 실제로 하나씩 다 밟았던 것들입니다.

**빌드 성공 ≠ 배포 완료 ≠ 화면 반영.** 세 단계가 전부 다릅니다. 로컬 빌드가 통과해도 푸시를 안 하면 안 올라가고, 배포가 성공해도 도메인 캐시가 옛날 걸 보여줄 수 있습니다. 한 단계씩 확인하세요.

**빌드가 실패하면 이전 배포가 그대로 유지됩니다.** 사이트는 멀쩡히 떠 있어서 성공한 것처럼 보이는데 내용은 옛날 버전입니다. 반드시 배포 대시보드에서 상태를 확인하세요.

**PowerShell 에서 `[` `]` 는 와일드카드입니다.** Next.js 의 동적 라우트 폴더(`app/[lng]/...`)를 지우거나 옮길 때 경로를 그냥 넘기면 `[lng]` 가 "l 또는 n 또는 g 중 한 글자" 패턴으로 해석되어 실제 폴더를 못 찾습니다. **오류도 안 나고 조용히 아무것도 하지 않습니다.**

```powershell
Remove-Item -LiteralPath "src\app\[lng]\seo.ts"    # -LiteralPath 필수
```

2026-08-27 죽은 코드 정리에서 실제로 발생했습니다. 13개 중 11개만 지워졌는데 AI 도구는 "완료했습니다"라고 보고했고 빌드도 통과했습니다(남은 2개가 어차피 미사용이라). **파일 목록을 직접 확인해서야 발견했습니다.** 같은 이유로 `public/` 파일 삭제는 잘 됐습니다 — 경로에 대괄호가 없었기 때문입니다.

**파일을 지웠다면 지워졌는지 목록으로 확인하세요.** "삭제했습니다"는 증거가 아닙니다. 특히 삭제 대상이 어차피 미사용 코드라면 빌드도 통과하므로 빌드 성공은 아무것도 보장하지 않습니다.

**AI 도구가 없는 데이터 필드를 지어냅니다.** "소재·색상으로 alt를 만들어줘"라고 하면 소재 데이터가 없어도 있는 것처럼 코드를 씁니다. 지시할 때 "추측하지 말고 타입 정의를 직접 확인해줘"를 반드시 넣으세요. `|| '기본값'`으로는 못 막습니다 — 타입스크립트는 실행 전에 막습니다.

**App Router에 `<head>`를 직접 열면 안 됩니다.** 정적 HTML 기준 지시문을 그대로 주면 AI가 이렇게 만듭니다. 지침서를 플랫폼별로 나눈 이유입니다.

**`generateMetadata`가 `alternates`만 반환하면 title·description이 상속됩니다.** 이전 지침서의 예제 코드가 정확히 이 형태였고, 그래서 canonical은 고쳐졌는데 메타 중복이 생겼습니다. 페이지마다 title·description도 함께 반환해야 합니다.

**`export const metadata`는 `params`를 못 봅니다.** 즉 `lng`를 모릅니다. 언어별 메타를 내보내려면 레이아웃에서도 `generateMetadata`를 써야 합니다.

**canonical에 `'/'`를 넣으면 모든 페이지가 루트를 가리킵니다.** 자기 주소로 자동 변환된다고 착각하기 쉬운데 그렇지 않습니다.

**openGraph는 얕게 병합됩니다.** 페이지에서 `openGraph.title`만 추가하면 레이아웃의 `images`·`siteName`이 통째로 사라집니다.

**CDN을 두 겹으로 쓰지 마세요.** Vercel 앞에 Cloudflare 프록시(주황 구름)를 세우면 배포해도 방문자는 옛날 페이지를 계속 봅니다. 회색 구름(DNS only)이 맞습니다.

**`public/`에 둔 파일은 그대로 서빙됩니다.** 테스트용 HTML을 여기 두면 구글이 색인합니다.

**사전 폴백(`dict.x || "한국어"`)은 번역 누락을 숨깁니다.** 폴백이 있으면 영·일·중 페이지에 한국어가 새어도 아무도 모릅니다. 폴백을 없애야 드러납니다.

**"완료했습니다"로 끝내는 지시를 하지 마세요.** AI에게는 항상 "실제 출력 HTML을 보여줘"까지 요구하세요. 보고서와 결과물은 다를 수 있습니다.

## 안티그라비티에 작업을 시킬 때 붙일 문장

`02_수정목록.md`의 항목을 붙여넣고 아래를 함께 넣으세요.

```
작업 규칙:
1. 추측하지 말고 타입 정의(node_modules/next/dist/lib/metadata/types/*.d.ts)와
   사전 JSON 구조를 직접 열어서 확인한 뒤 코드를 써라.
2. 수정 후 npm run build를 실행하고 출력 원문을 그대로 보여줘라.
   라우트 목록에서 정적(○)/동적(ƒ) 표시가 바뀐 게 있으면 명시해라.
3. npm run start 후 해당 페이지의 렌더된 <head>를 curl로 뽑아 보여줘라.
   "적용했습니다"만으로 끝내지 마라.
4. 여러 페이지·여러 언어를 비교한 결과를 표로 보여줘라.
   같은 값이 반복되면 아직 안 고쳐진 것이다.
```
