# 작업 규칙 (항상 적용)

이 문서는 매 작업마다 자동으로 지켜지는 규칙입니다. 매번 다시 말하지 않아도 됩니다.

---

## 역할 분담

프로그램을 모르셔도 되도록 나눴습니다.

| 누가 | 무엇을 |
|---|---|
| **Claude** | 코드를 읽고, 원인을 찾고, **파일을 직접 고쳐서 폴더에 써넣기.** 결과 검증과 판독 |
| **안티그라비티** | 빌드 실행, 커밋, 푸시 — **판단이 필요 없는 명령만** |
| **사용자** | 배포 상태 확인, 브라우저에서 눈으로 확인. 그리고 방향 결정 |

Claude는 이 환경에서 명령 실행(`npm`, `git`)과 파일 삭제를 할 수 없습니다. 그 세 가지만 안티그라비티나 사용자가 대신합니다. **코드 판단은 안티그라비티에 맡기지 않습니다.**

---

## git 규칙 (반드시)

안티그라비티에 커밋·푸시를 시킬 때는 항상 이 문장을 넣습니다.

```
amend 하지 말고 새 커밋으로 만들어줘.
force push(--force, -f) 는 절대 쓰지 마.
푸시 결과 출력을 그대로 보여줘.
```

**왜 중요한가.** `git commit --amend`는 직전 커밋을 지우고 새로 만듭니다. `git push --force`는 원격 저장소의 기록을 통째로 덮어씁니다. 다른 작업이 섞여 있었다면 그게 흔적 없이 사라집니다. 되돌릴 방법이 없습니다.

2026-08-26 프로토타입 HTML 삭제 작업에서 안티그라비티가 시키지도 않은 `--amend`와 `--force`를 썼습니다. 그때는 운 좋게 삭제 커밋 하나뿐이라 손실이 없었지만, 다음에도 그러리라는 보장이 없습니다.

정상적인 커밋은 이렇게만 하면 됩니다.

```
git add -A
git commit -m "메시지"
git push
```

## 한 번에 하나씩

한 커밋에 한 가지 변경만 담습니다. 여러 개를 묶으면 문제가 생겼을 때 어느 것 때문인지 알 수 없습니다.

작업 하나의 흐름은 항상 이렇습니다.

```
1. Claude가 파일을 고쳐서 폴더에 써넣음
2. 안티그라비티: 빌드 → 출력을 Claude에게
3. Claude가 빌드 출력 확인
4. 안티그라비티: 커밋 → 푸시
5. 사용자: Vercel 대시보드에서 Ready 확인
6. 사용자: 브라우저에서 결과 확인 (Ctrl+Shift+R)
7. Claude가 라이브에서 재확인 후 다음 단계
```

**5번을 건너뛰지 마세요.** 빌드가 실패하면 이전 배포가 그대로 유지됩니다. 사이트는 멀쩡히 떠 있는데 내용만 옛날 버전인 상태가 되고, 이걸 모르면 "왜 안 바뀌지"를 한참 헤매게 됩니다.

## 안티그라비티에 넘기는 표준 문장

**빌드 요청**

```
npm run build 를 실행하고 출력을 전부 그대로 보여줘.
요약하지 말고 라우트 목록까지 포함해줘.
에러가 나면 고치려 하지 말고 에러 내용만 그대로 보여줘.
```

**커밋·푸시 요청**

```
git add -A 하고 아래 메시지로 새 커밋을 만들어서 푸시해줘.
메시지: <여기에 메시지>

amend 하지 말고 새 커밋으로 만들어줘.
force push(--force, -f) 는 절대 쓰지 마.
푸시 결과 출력을 그대로 보여줘.
```

이 두 개면 대부분 끝납니다.

## 안티그라비티에 코드를 맡겨야 할 때

원칙적으로 맡기지 않지만, 불가피하면 이 세 문장을 반드시 넣습니다.

```
추측하지 말고 관련 파일과 타입 정의를 직접 열어서 확인한 뒤 작업해줘.
시킨 것 외에는 아무것도 바꾸지 마. 리팩터링 하지 마.
수정 후 실제 출력(빌드 로그, 렌더된 HTML)을 보여줘. "완료했습니다"로 끝내지 마.
```

**"완료했습니다"는 증거가 아닙니다.** 이 프로젝트에서 반복적으로 문제가 됐던 지점입니다.

```

public/sitemap.xml     ← 같음
.env.local             ← 문의 폼 설정. 지우면 문의가 안 옴
```
