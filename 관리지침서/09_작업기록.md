설비 사진이 5504×3072 였습니다. 배경으로 쓰이는 이미지인데 웹에서 필요 없는 해상도라 장당 99% 줄었습니다.

**왜** 쇼룸 제품 사진은 화면에 280×320px 로 표시되는데 원본이 2048×2048 PNG 였습니다. PNG 는 사진에 맞지 않는 포맷이고, 해상도도 표시 크기의 7배였습니다.

**도구** `scripts/optimize-images.mjs` (신규). 세 가지 모드:
- `convert` — 200KB 이상 이미지를 축소·변환. **원본은 지우지 않음**
- `verify` — `src/` 가 참조하는 모든 미디어 경로가 `public/` 에 실제로 존재하는지 검사
- `prune` — verify 통과 시에만, 아직 참조되지 않는 원본만 삭제

**이 순서가 핵심입니다.** 이미지 경로가 틀리면 **빌드는 멀쩡히 통과하고 배포 후에야 사진이 깨져 보입니다.** verify 가 그걸 배포 전에 잡습니다.

**중간에 잡은 것** 1차 prune 에서 원본 63개가 "아직 참조됨"으로 남았습니다. 사전(`locales/*.json`)의 **사용되지 않는 `showroom.products` 배열**이 여전히 `.png` 경로를 들고 있었기 때문입니다. 안전장치가 제대로 작동한 사례입니다 — 참조가 남아 있으면 지우지 않습니다. 사전 4개의 경로 316건을 `.webp` 로 바꾼 뒤 2차 prune 에서 전부 정리됐습니다.

**함께 고친 것** JSON-LD 의 회사 로고 주소가 `https://www.primedaon.com/logo.png` 였는데 **그 파일이 존재하지 않았습니다(404 확인).** 검색결과에 회사 로고가 표시되지 않고 있었습니다. `/images/CI.png` 로 수정.

### ✅ 서치콘솔 사이트맵 정리 (2026-08-27)

**무엇** 옛 non-www 사이트맵 항목(`https://primedaon.com/sitemap.xml`, 2026-07-17 제출) 삭제. 이제 `https://www.primedaon.com/sitemap.xml` **한 줄만** 남았고 발견된 페이지 **28**.

**왜** 두 항목이 나란히 있으면서 옛 것은 23, 새 것은 28 로 숫자가 갈려 있었습니다. 다음에 이 화면을 볼 때 어느 쪽이 맞는지 혼동을 일으킵니다.

**삭제 전 확인한 것**
- 속성이 도메인 속성이라 www / non-www 데이터가 어차피 한 속성에 합산됨
- apex 와 www 양쪽 robots.txt 가 모두 `Sitemap: https://www.primedaon.com/sitemap.xml` 을 가리킴 → 삭제 후 "감지된 사이트맵"으로 재등장하지 않음

**중요** 사이트맵 항목 삭제는 **제출 기록만** 지웁니다. 이미 색인된 페이지는 검색결과에서 빠지지 않습니다.

⚠️ Sitemaps 화면 안의 '사이트맵 삭제' 와 좌측 메뉴의 '삭제(Removals)' 도구는 완전히 다릅니다. Removals 는 URL 을 검색결과에서 약 6개월간 숨기는 기능이라, 도메인을 넣으면 사이트가 통째로 사라집니다. **반드시 Sitemaps 화면 안에서만** 작업할 것.

**최종 상태** 서치콘솔 사이트맵: www 1건, 상태 성공, 발견된 페이지 28. 생성 파일·라이브·서치콘솔 세 곳 숫자 일치.
